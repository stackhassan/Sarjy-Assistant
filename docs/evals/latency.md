# Latency: guardrails on vs off

_Generated by `npm run evals:latency` on 2026-09-29 13:34 UTC — 60 live turns (3 reps × 10 prompts × guards on/off, order alternated). 2 turn(s) served by a fallback model because of free-tier rate limits were excluded so both arms use the same model._

All times in ms, measured server-side from request start. "First sentence" is when the first screened, signed sentence is emitted, the moment the client can start TTS.

| **First sentence**, chat | 2254 / 4778 | 1144 / 3358 | +1110 | 17 / 18 |

| Total turn, all | 2394 / 8640 | 1942 / 4999 | +452 | 29 / 29 |

**About the +1.1 s:** the guards don't cause it. In these samples the gap is entirely in the chat model's *first token* (the guards finish in ~154 ms, and `guardWait` is 0), which pointed at either the guard calls competing with the chat request on the same Groq key, or noise. A dedicated interleaved test ([contention.md](contention.md)) found no competition. Chat first token was 326 ms with both guard calls fired alongside versus 439 ms alone, and Groq's own `queue_time` was the same either way (244 vs 263 ms). Full turns: 591 ms to first sentence with guards on versus 619 ms off (p50, n = 12 each). The earlier gap came from this run happening on a slow day for Groq (first tokens around 2 s, versus about 0.5 s in the contention run), where its heavy tail dominates 17–18 samples. On Groq, the guard models also have their own per-model rate limits, so they don't use up the chat model's tokens per minute.

## Where guard time goes (guards ON)

| Measure | p50 | p95 | n |
|---|---|---|---|
| L1 + L2 input guards (parallel), wall time | 154 | 427 | 29 |
| LLM first token (runs concurrently with the above) | 2233 | 8223 | 29 |
| **guardWait**: first sentence ready → allowed out | 0 | 4 | 29 |
| L4 per sentence (deterministic tier; LLM tier only on risk) | 0 | 1 | 29 |
| Prompt Guard 2, standalone | 123 | 284 | 8 |
| gpt-oss-safeguard (topic policy), standalone | 141 | 204 | 8 |

**Reading this:** input guards take ~154 ms but run *alongside* the LLM, whose first token takes ~2233 ms, so by the time a sentence is ready the guards are usually done. `guardWait` is the real cost users feel. If the guards ran *before* the LLM (the naive design) every turn would pay the full ~154 ms up front.
